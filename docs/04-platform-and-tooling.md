# 04 — Platform and tooling

## The stance in three lines

1. **Local, free, and nothing else.** Every stage runs on the learner's laptop with tools that cost nothing and need no account. The one account (GitHub, stage 2) is free and exists so the portfolio has a public home.
2. **One tool per job, the one a tier-1 team would use today.** `uv` for environments and packages, `pytest` for tests, `ruff` for lint and format, `mypy` for types, git for history, the editor's debugger for stepping. No alternatives are taught; the briefs say why each one.
3. **Standard library first.** Two third-party packages appear in the whole course, both at stage 6, both after the standard-library way has been shown.

## Why local and free

A beginner's first program must not depend on a network, a login or a credit card. Every failure in the first ten hours should be a Python failure, not an account failure. Local also means the learner sees where files live, which is itself a destination skill (`pathlib`, working directories, relative paths — stage 5).

## The toolchain, and why each piece

Exact versions and install links are pinned in [`PINS.md`](../PINS.md); briefs refer to roles.

| Role | Tool | Why this one | Arrives |
|---|---|---|---|
| Interpreter | CPython, the pinned minor | The reference implementation; the version the sibling courses assume on entry. Installed from python.org in stage 0 because a wizard-driven installer is the right first install; managed by `uv` from stage 1 onward. | s00 |
| Editor | Visual Studio Code + Python extension | Free; the most common editor in Python teams; the debugger is one click; the integrated terminal means the learner never leaves one window. The extension bundles the debugger. AI completion is turned off until stage 7. | s00 |
| Terminal | the operating system's own | Windows Terminal/PowerShell or macOS Terminal. The terminal is a destination skill; a third-party shell would add vocabulary. | s00 |
| Environments and packages | `uv` | One tool replaces `pip`, `venv`, `pyenv` and `pip-tools`; `uv run` means the learner never activates an environment by hand; `uv add` writes `pyproject.toml`; `uv build` ships. The fastest path from "clone" to "tests run". | s01 |
| Command runner | `just` | Standard commands (`just test`, `just eval`) so every stage runs the same way; a `justfile` is readable by a beginner where a Makefile is not. Installed with `uv tool install`. | s01 |
| Version control | git, then GitHub | Save points first (stage 1: `init`, `add`, `commit`, `log`); a remote and a pull request when there is enough work to protect (stage 2). | s01, s02 |
| Tests | `pytest` | The test runner Python teams use; plain `assert`; readable failures; `parametrize` and fixtures when the learner is ready for them (stage 6, 9). Run from stage 1, written from stage 6. | s01 |
| Lint and format | `ruff` | One fast tool for both; its rules name the quiet failures (`B006` mutable default, `E722` bare except, `S307` eval) so the linter is also a teacher. `check` at stage 2, `format` at stage 9. | s02 |
| Types | `mypy` | Type hints are written from stage 4 so they are habit; checked from stage 9 so the first years of hints are documentation, not a wall. `--strict` on the capstone. | s09 |
| Debugger | `breakpoint()` and the editor's debug pane | Built in; `pdb` first so the learner knows what the pane is doing. | s04 |
| Logging | `logging` | Standard library; a logger per module; the record of what a program did to files. | s05 |
| Timing and profiling | `timeit`, `cProfile` | Standard library; numbers before adjectives. | s09 |
| Coverage | `pytest-cov` | ≥ 90 % on the capstone; the number that says which lines no test has ever run. | s09 |

## Third-party packages

Two, at stage 6, after the standard-library alternative has been used:

- **HTTP client** (`requests`): after `urllib.request`, so the learner sees what the package saves. Against the public API pinned in `PINS.md` — no key, small JSON, fits the library theme. An offline sample is in the fixture for days the network is down.
- **Terminal output** (`rich`): tables and colour for the command-line programs; the exercise is as much about reading a package's documentation as about the output.

Nothing else. No `pydantic`, no web framework, no data-science stack, no notebook. The sibling courses add those.

## Fixtures

One purpose-built, seeded, synthetic world — a neighbourhood library — generated by `data/build_files.py` (see [`data/README.md`](../data/README.md)). CSV, JSON and a messy line-oriented text file, plus deliberately broken copies. Used from stage 3 as literals, from stage 5 as files, and persisted to by the capstone. No external dataset anywhere.

## Platforms

Windows and macOS are both first-class; the stage-0 brief gives both sets of commands where they differ (the Python command name, how to open a terminal, `uv`'s install line). Linux learners follow the macOS column. From stage 1, `uv run python` makes the command identical everywhere.

## What is deliberately not here

- Notebooks. The artefact is always a program in a file, run from the terminal, with tests.
- Docker, cloud, CI beyond the repository's own checks. A junior meets these in week two of the job, not week one.
- Alternative tools (conda, poetry, black, flake8, unittest, pdb++). The learner who knows one tool well can learn the alternative in an afternoon; the learner who has seen five knows none.
